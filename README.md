# coep-unitime-pilot

Semester VII pilot that turns a Taasika snapshot into a UniTime timetable for the Department of Computer Engineering, scores that timetable independently of the solver, and tests whether a learned neighbourhood selector beats a weight-tuned stock solver.

The reinforcement-learning comparison was not run. What was run is a weight sweep of the stock solver, a smoke test of the learning layer on a synthetic instance, and a baseline bake-off on an instance that was already conflict-free. This file records the decisions behind those runs, the numbers they produced, and the work still open. Build and operator detail stays in `rl/README.md` and `rl/SETUP.md`. The Data Exchange files are described in `unitime-out/README.md`.

`rl/runs/` is listed in `rl/.gitignore`, so the metric files cited below are local run output. They are not in the git history.

## Decisions the runs depend on

**The solver must actually load students.** The stock configuration reads projected demand. This session has none, so a load under that setting exports an empty `<students/>` block and reports zero conflicts. Headless runs use a solver XML produced with *Enrolled Student Course Demands*, which reads the imported `StudentClassEnrollment` rows. The Spr6 export that the sweep uses, `rl/instances/spr2026.xml`, contains 990 of the 1,290 simulated students. The other 300 are absent from that export. They are not dropouts.

**The policy does not place classes.** `RlNeighbourSelection` chooses among eight operators that already exist in CPSolver. Every proposal is generated by a stock operator and accepted or rejected by Great Deluge. Hard constraints are the solver's, not the policy's. If ONNX inference times out, the wrapper falls back to the stock selector.

**Training and production are different processes.** Training is Python (Maskable PPO, Gymnasium) driving JVM workers over gRPC. Production loads a frozen ONNX policy inside the solver JVM. The recorded training arguments in `rl/models/ppo/train_args.json` are 100,000 timesteps, three workers (`localhost:50051`–`50053`), instance `spr2026`, and a behaviour-cloning initialisation from `models/bc_policy.pt`.

**The 25% bar is a held-out comparison, and the sweep script treats a different test as that bar.** The run plan in `rl/README.md` is: freeze a B0 baseline, sweep the student-conflict weight for arm B1, train on one term, and bake off arms B0, B1, B2, L, and R on a held-out term under the same wall-clock budget. The success test for the learned policy (arm R) is a 25% relative reduction against the tuned baseline (B1) on that held-out instance. `weight_sweep.py` instead prints "B1 ALONE CLEARS 25%" when B1's median on the *same* instance is 25% below B0. That line in `rl/runs/sweep/summary.md` is the script's reading. It is not the held-out comparison, which was not run.

**B0 and B1 at weight 0.2 are the same configuration.** Both use `FixCompleteSolutionNeighbourSelection` and `TimetableComparator`. B1 only changes the student-conflict weight, and it moves `Comparator.StudentConflictWeight` together with the two placement-selection weights. At 0.2 there is nothing to move. A difference between those two medians is seed noise.

**Student switching was turned off for the institutional timetable, not for the headless sweep.** UniTime's final sectioning pass can move a student between laboratory batches and report the overlaps as solved. The server runs that produced a conflict count for the department were made with *Enrolled Student Course Demands*, `General.SwitchStudents=false`, and `Global.LoadStudentEnrlsFromSolution=true`. The headless sweep does not use that pinning. Its violation rate is the solver's own student block.

**Times from Taasika are not copied in as the answer.** Course offerings are exported without a `<time>` element, so the solver assigns times instead of reproducing the manual timetable. Room associations are preferences, not pre-assignments. The lunch window (one free hour between 11:30 and 15:30) is applied by `scripts/setup_lunch_breaks.py` inside UniTime before the solve, not by the learning layer.

**Students in the generated dataset are synthetic.** Real MIS extracts were not available. Identifiers have the shape `61yy03aaa`, but `yy` is 01–05 for first year through M.Tech. A real MIS number uses those two digits as the admission year. The two schemes must not be read as the same.

## Results

### Weight sweep

Medians as archived in `rl/runs/sweep/summary.md`. Assigned ratio is 1.00 on every row.

| Arm | Weight | Median C | Soft penalty |
| --- | ---: | ---: | ---: |
| B1 | 0.2 | 0.0343 | 62 |
| B1 | 0.5 | 0.0192 | 66 |
| B1 | 1 | 0.0263 | 67 |
| B1 | 2 | 0.0030 | 65 |
| B1 | 5 | 0.0000 | 69 |
| B1 | 10 | 0.0040 | 64 |

B0, same instance and the same selector, median C = 0.0414 (seeds 0.0414, 0.0263, 0.0515). B1's three seeds at the same weight are 0.0343, 0.0556, and 0.0202. The two medians differ by about 17%. That is the seed noise, not an effect of the weight.

The median of every weight falls below 0.06, with all 262 classes assigned, from a start of 0.5313. Two individual B1 seeds do not: 0.0778 at weight 0.5 and 0.0616 at weight 1. Most of the drop from 0.5313 is the search, not the weight.

Against the B0 median of 0.0414, weight 1 is only a 36% reduction (median 0.0263). The best weight in the per-seed files now on disk is 2, at 0.0030, a 92.7% reduction. The archived summary instead picks weight 5 at C = 0 and prints a 100% reduction. Recomputing the median from the three weight-5 files gives 0.0263 (seeds 0.0263, 0.0000, 0.0444), so weight 2 is the minimum. One of those three seeds appears to have been repeated after the summary was written. The sweep stores 21 metric files: three seeds at each of seven configurations. Weight 5 has three files, not fifteen.

Neither reading is the 25% test the learned policy was written for. A 25% gain on C = 0.0030 would be a change of about one student in 990, which three seeds cannot resolve.

### Bake-off

On `spr2026_10m_w5`, B0, B1, and B2 all finish at C = 0, which is the value the instance already had when it was loaded. The run cannot separate a learned policy from a fixed one, and arms L and R were not included.

### Synthetic smoke test

On the 120-class instance, B0, B2, the random wrapper, and LinUCB all finish at C = 0.133. The behaviour-cloned ONNX policy finishes at 0.267 and collapsed onto one operator. Throughput was about 100 macro-steps per second per worker. An ONNX forward pass was about 0.08 ms, and the PyTorch-to-ONNX deviation on that export was 2e-6. These numbers check that the pipeline runs. They are not evidence about the department's timetable.

### A solver export that is not an RL result

`solutions/kpi_report.json`, which is checked in, scores an earlier CSV export: 587 of 1,290 students conflicted (45.5%), 260 of 261 classes assigned, hard feasibility 94.98. That file and the sweep measure different populations. The sweep's denominator is the 990 students inside the solver XML. The CSV report's denominator is every student in the enrolment file it was joined to.

The later pinned-enrolment solve (switching disabled) is a different artefact, `unitime-out/spr2026_11_all_flags.csv`, and it is not committed on this branch. Scored against the current dataset it has 290 of 291 classes assigned, no instructor or room double-booking, and 40 of 1,130 students in conflict, all of them first-year students in four laboratory placements against the reserved lecture block.

## Future work

Carried over, and not done:

- Examination scheduling. Periods are present in the session file. No examination elements are emitted, and Taasika does not model exams.
- An `.ics` export.
- A second department. The pipeline is parameterised by snapshot and term, but only Computer Engineering has been loaded and solved.
- Automated change notification, and the WhatsApp group automation. Neither has been started.
- A real MIS extract in place of the simulated students. The generator is the only piece that would change.
- A teacher-facing availability screen. Preferences today are whatever the Taasika snapshot contains.
- Two instructors blocked together, for the same students, in the same room, as one distribution constraint.

Opened by this phase:

- Put the 40 remaining first-year conflicts into the model as different-time constraints between the programming laboratory and the reserved lecture block, instead of paying for them only through the student-conflict weight.
- Represent batches as group reservations, so the solver can re-section inside a batch without the switching pass that was turned off.
- Raise the room-preference hit rate. On the pinned solution it is 12.59%, the worst measured rate.
- Make the instructor-identity check compare names after normalising them. It currently scores 0% because the two sides use different name formats, and that zero pulls the preference score down.
- One command from a Taasika snapshot to a scored solver XML, using the headless runner, so the import clicks in the UniTime UI are not on the path.
- Write a solved timetable back into a Taasika snapshot.
- Run arms L and R against B1 on a held-out term, same wall-clock budget, on an instance that is not already conflict-free. Until that exists, the layer is instrumentation (the conflict oracle, the state encoder, the headless runner), not a solver result.
- Fix the input defects that manufacture conflicts: the over-subscribed M.Tech laboratory, cross-division batches, empty groups, and stale laboratory sections.
